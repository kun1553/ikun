## 一门让我重新认识机器的课

《深入理解计算机系统》我读得很慢，从暑假一直读到十一月。它不是读一遍就能刷完的书，但每读完一章，我对「程序在机器上到底发生了什么」的理解都会往前走一点。这篇笔记记录三个印象最深的点，都不是新知识，而是原本以为自己懂、读完之后才发现不懂的东西。

## 存储层次与局部性

第 6 章把存储层次画成一个金字塔：寄存器、L1/L2/L3 缓存、内存、磁盘，越往上越快越小越贵。关键在于相邻层之间的访问速度差好几个数量级——L1 命中大概 1 纳秒，内存要 100 纳秒左右，磁盘就更不用说。

这意味着程序性能的关键不是「指令条数少」，而是「访问的数据尽量落在缓存里」。能不能落进去取决于局部性：时间局部性（刚访问过的数据很可能再被访问）和空间局部性（访问了某个地址，它附近的数据很可能接着被访问）。

## 一个双重循环，差了将近十倍

书里有个经典例子，我照着在 WSL 里跑了一遍。定义一个 4096 × 4096 的全局 int 数组，也就是 64 MB，明显超过常见的 L3 缓存，然后用两种顺序求和：

```c
#include <stdio.h>
#include <time.h>

#define N 4096
int a[N][N];

int main(void) {
    for (int i = 0; i < N; i++)
        for (int j = 0; j < N; j++)
            a[i][j] = i + j;

    long sum = 0;
    clock_t t1 = clock();
    for (int i = 0; i < N; i++)
        for (int j = 0; j < N; j++)
            sum += a[i][j];      /* 按行，相邻访问，步长 1 个 int */
    clock_t t2 = clock();

    long sum2 = 0;
    for (int j = 0; j < N; j++)
        for (int i = 0; i < N; i++)
            sum2 += a[i][j];     /* 按列，每次跨一整行 */
    clock_t t3 = clock();

    printf("row  %.3f s  sum=%ld\n", (double)(t2 - t1) / CLOCKS_PER_SEC, sum);
    printf("col  %.3f s  sum=%ld\n", (double)(t3 - t2) / CLOCKS_PER_SEC, sum2);
    return 0;
}
```

用 `gcc -O2 loop.c -o loop` 编译，实测输出：

```text
row  0.098 s  sum=34358689792
col  0.871 s  sum=34358689792
```

结果一样，时间差了将近九倍。原因不复杂：C 语言的多维数组是行优先存储的，`a[i][j]` 的地址等于 `a + (i * N + j) * 4`。按行遍历时，访问完 `a[i][j]` 紧接着访问 `a[i][j+1]`，两个地址相邻，一个 64 字节的缓存行能装 16 个 int，命中率极高。按列遍历时，从 `a[i][j]` 到 `a[i+1][j]` 跳了 `N * 4 = 16 KB`，缓存行里另外 15 个 int 全被浪费掉，而且 16 KB 的跨度很快就把缓存挤满，下一次迭代基本必然缺失。

这个实验让我第一次直观感受到：同样的算法、同样的运算次数，内存访问模式不同，性能可以差一个数量级。后来写 Java 处理矩阵、写 SQL 琢磨索引的时候，我都会下意识想一想数据是怎么被读进内存的。

## 虚拟内存与栈溢出

第 9 章讲虚拟内存，把我以前零零碎碎知道的概念串了起来：每个进程都以为自己独占一整块连续的地址空间，实际由页表映射到物理页；缺页时触发异常，操作系统把磁盘上的页换进来。进程之间互不干扰，是因为它们的虚拟地址到物理地址的映射完全不同。

栈溢出也从「一个名词」变成了可预测的现象。默认线程栈是 8 MB，我在 WSL 里用这个函数试了一下：

```c
void recurse(int depth) {
    char buf[4096];   /* 每层递归压 4 KB 栈帧 */
    printf("%d\n", depth);
    recurse(depth + 1);
}
```

程序打印到 2000 多层的时候收到了 SIGSEGV。算一下就对上了：8 MB 除以 4 KB 大约是 2048。用 `ulimit -s` 能看到这个限制，改成 `ulimit -s 65536` 之后再跑，能递归的层数也跟着涨到一万多层。以前只知道「递归太深会栈溢出」，现在知道它有明确的数字边界，而且每个局部数组的大小都在消耗这个预算。

## 浮点数：0.1 + 0.2 为什么不是 0.3

第 2 章讲 IEEE 754 浮点表示，我顺手验证了那个流传很广的例子：

```c
printf("%.20f\n", 0.1 + 0.2);        /* 0.30000000000000004441 */
printf("%d\n", 0.1 + 0.2 == 0.3);    /* 0 */
```

原因在于 0.1 和 0.2 在二进制下都是无限循环小数，双精度只有 52 位有效位，存进去的时候就已经带了一个很小的舍入误差，相加之后误差被保留下来。这不是语言的 bug，是二进制表示的固有限制。

这件事对我写业务代码的影响很具体：金额相关的地方用 `BigDecimal`，比较浮点数时不用 `==`，而是看差值绝对值是否小于某个容差。以前我是把这两条当规则背下来的，读完这一章之后，规则背后的原因清楚了，也就不容易在规则没覆盖到的地方犯错。

## 一点感想

这本书最大的价值不是教了我多少新知识，而是把很多我之前「知道结论」的东西变成了「能解释为什么」。存储层次解释了我以前不明白的性能差异，虚拟内存解释了进程隔离和段错误，浮点表示解释了那些看起来莫名其妙的精度问题。读得慢一点其实没关系，能自己动手验证一遍的，收获会比读完记住的多。
